## 二、面试问答

### Q1：为什么不用 Celery / Redis / Kafka？

**一句话回答**：在这个规模下，额外的基础设施是负债而不是资产，而 PostgreSQL 恰好提供了我需要的全部队列语义。

**展开**：

用消息中间件要付出这些代价：

1. **多一个必须部署、监控、处理故障的组件。** 免费平台的环境下尤其明显——它们通常只给一个 Web Service，加 Redis 或 Kafka 意味着要么付费要么自己找地方托管。
2. **一致性问题。** 队列消息在 Redis、业务数据在 PostgreSQL，是两个系统，没有共同的事务边界。会出现"任务入队成功但业务记录没写"这类中间状态，需要补偿逻辑去兜。
3. **本地开发成本。** 拉下代码要额外起一个容器才能跑起来。

而我需要的队列语义只有一条：**多个消费者并发取任务且彼此不阻塞**。这正是 `FOR UPDATE SKIP LOCKED` 提供的。加上任务和业务数据本来就在同一个库里，事务边界天然共享——事件入库和任务可被取用是同一个 commit 完成的，不存在中间态。

**追问：那什么时候该换掉？**

队列表是持续 `INSERT` + 状态更新的模式，会产生大量死元组，靠 autovacuum 回收。当前单机入站约 380 事件/秒，离 PostgreSQL 单表写入瓶颈还有距离，但这个距离不是无限的。真要横向扩展，第一个改动点是把 `events` 表按 `endpoint_id` 分区，让索引和维护成本随单个 endpoint 的数据量而不是全表增长。

**追问：这不就是"轮询数据库"吗，不 low 吗？**

要看具体在做什么。无脑 `SELECT ... WHERE status='pending'` 全表扫确实很糟——那会随着表变大线性变慢。但这里有两点不同：一是建了**部分索引**（只索引 `pending` 状态的行），所以索引体积只与待处理量相关，与历史总量无关；二是查询条件带 `next_attempt_at <= now()` 且 `ORDER BY next_attempt_at`，索引直接覆盖。实测执行计划是 `Index Scan using ix_events_pending_due`，`Execution Time: 0.035 ms`，且 `Buffers: shared hit=1`。

### Q2：`FOR UPDATE SKIP LOCKED` 和普通 `FOR UPDATE` 有什么区别？

**一句话回答**：`SKIP LOCKED` 让第二个 Worker **跳过**被锁的行，普通 `FOR UPDATE` 让它**等待**——等待就意味着串行化，多个 Worker 的并发能力直接归零。

**展开**：

假设两个 Worker 同时取任务：

- 普通 `FOR UPDATE`：Worker A 锁住第 1 行，Worker B 的查询也要第 1 行，于是 B 阻塞等 A 提交事务。等到了之后 B 才继续。结果是两个 Worker 实际上一前一后地干活。
- `FOR UPDATE SKIP LOCKED`：Worker B 发现第 1 行被锁，直接跳过它去取第 2 行。两个 Worker 各拿各的，真正并行。

取任务的完整 SQL：

```sql
SELECT * FROM events
WHERE status = 'pending' AND next_attempt_at <= now()
ORDER BY next_attempt_at
LIMIT 50
FOR UPDATE SKIP LOCKED
```

三个子句各自有作用：

- `next_attempt_at <= now()`：只取到期的，没到重试时间的跳过（这是退避能生效的原因）
- `ORDER BY next_attempt_at`：先到期的先投，避免老任务被一直在后面插队的新任务饿死
- `LIMIT 50`：一次取一批减少数据库往返，但**这和并发投递是两件事**——取 50 条，同时只投 10 条（由 `asyncio.Semaphore` 控制），避免瞬间对下游打 50 个连接

**关键细节**：SELECT 和随后的 UPDATE（标记为 `delivering`）**必须在同一个事务里**。否则中间有个窗口——任务被选中但还没标记，另一个 Worker 的查询会再次选中同一条，同一个事件被投递两次。

### Q3：投递语义为什么定为"至少一次"？为什么不做"恰好一次"？

**一句话回答**：跨进程的"恰好一次"在工程上做不到，因为存在本机无法判断的状态。承认做不到，比假装做到了更可靠。

**展开**：

投递失败可能发生在任意一步，其中有几个是"不可判定"的：

| 情形 | 本机能知道吗 | 该怎么办 |
| --- | --- | --- |
| 连接都没建立起来 | 能，对端没收到 | 安全重试 |
| 请求发出，对端返回 500 | 能，对端明确失败 | 安全重试 |
| 请求发出，超时无响应 | **不能** | 重试可能重复、不重试可能丢失 |
| 对端处理成功，但响应在返回路上丢了 | **不能** | 同上 |
| 对端处理成功，但写库前进程被杀 | **不能** | 同上 |

最后三种情况下，"重试"和"不重试"都可能出错——这不是代码写得不够好，而是分布式系统的固有性质。

所以我选择**保证送达**（至少一次），同时把去重的工具交给下游：每次投递带上 `X-HookRelay-Delivery-Id`，**同一个事件的所有重试共享同一个 ID**，下游按它做幂等即可。这样责任划分是明确的：我保证不丢，你保证不重复处理。

**追问：那下游不做去重怎么办？**

那就是业务问题而不是投递问题。我在文档里明确写了这一点（`docs/USAGE.md` 和 README 的已知局限），而不是含糊地说"支持精确一次"让使用者误以为不用管。对外承诺比实际能力大，是最容易埋雷的做法。

### Q4：死信重放为什么需要 `attempt_generation` 这一列？

**一句话回答**：因为 `delivery_attempts` 表上有 `(event_id, generation, attempt_number)` 唯一约束，只把 `attempt_count` 清零的话，新产生的"第 1 次尝试"会和历史记录撞车，插入直接失败。

**展开**：

最初的设计很简单：`attempt_count` 记录试过几次，`delivery_attempts` 记录每次的结果，唯一约束是 `(event_id, attempt_number)`。重放时把 `attempt_count` 清零、状态改回 `pending`。

然后问题出现了：清零之后第一次投递会生成"第 1 次尝试"的记录，而历史里已经有一条"第 1 次尝试"（上一轮的那次），唯一约束冲突，插入报错，整个重放流程挂掉。

两种修法：

- **删掉旧记录**：简单，但丢失排查问题最需要的信息——"这个事件被投过几次、每次都返回了什么、为什么最终进了死信"。
- **加轮次标记**：`generation` 从 0 开始，重放时 `+1`，唯一约束变成 `(event_id, generation, attempt_number)`。历史记录完整保留，新记录落在新轮次。

我选了第二种。**排查问题时投递历史是核心信息，不能为了省一列把它覆盖掉。**

**顺带一个约束**：重放只允许在 `dead` 或 `succeeded` 状态下发起，`pending` / `delivering` 时返回 `409 Conflict`。这不是多余的校验——正在投递的事件如果被重放，会导致同一个事件被两个 Worker 同时处理。

### Q5：幂等为什么靠唯一索引，而不是"先查后写"？

**一句话回答**：`SELECT` 判断不存在再 `INSERT` 这个写法有竞态，两个请求可能同时通过检查然后都插入。数据库的唯一约束是原子的，不存在这个窗口。

**展开**：

有问题的写法：

```python
existing = await session.scalar(select(Event).where(Event.idempotency_key == key))
if existing is None:
    session.add(Event(idempotency_key=key, ...))
    await session.commit()
```

两个请求同时执行时：都查到 `None`（因为对方还没提交），都执行插入，结果两条重复记录。加锁能修，但引入锁争用，还要考虑锁粒度。

正确的做法是**把判断交给数据库**：

```python
session.add(Event(idempotency_key=key, ...))
try:
    await session.commit()
except IntegrityError:
    # 唯一冲突 = 已存在，按重复事件处理，返回 202
```

唯一约束的检查与插入是同一个原子操作，在数据库内部完成，应用层拿不到中间状态。

**另外一个设计点**：调用方可能根本不传幂等键。这时用**请求体的 SHA-256** 作为兜底——同一个 endpoint 收到字节完全相同的请求体，视为重复。这覆盖了"上游超时重发"这个 Webhook 世界里最常见的重复场景（很多上游根本不支持幂等键）。

**追问：返回 202 还是 409 表示重复？**

我返回 `202 Accepted`，同时在响应里标注是重复事件。理由是从调用方视角看，**重复提交的结果和首次提交是一样的**——事件确实在系统里、确实会被投递，调用方的目的达到了。返回 409 会诱导调用方去做错误处理，而实际上什么都不需要做。

### Q6：Worker 中途被杀了，正在投递的任务怎么办？

**一句话回答**：任务在取走时被标记为 `delivering` 并记录 `locked_at`，超过锁超时时间仍未完成的任务会被其他 Worker 回收为 `pending` 重新投放。

**展开**：

流程是这样的：

1. Worker 取任务时，在同一事务里把 `status` 改成 `delivering`，写入 `locked_at`（当前时间）和 `locked_by`（自己的标识）
2. 投递完成后，把状态改成 `succeeded` 或回到 `pending`（等重试）
3. 如果 Worker 在这中间被 `kill -9`，任务永远停在 `delivering`

第 3 种情况靠**僵尸任务回收**兜底：Worker 每 60 秒检查一次有没有 `status='delivering' AND locked_at < now() - lock_timeout` 的任务，有就改回 `pending`。

**这里有个刻意的选择**：回收时**不清零** `attempt_count`。

原因是清零会让一个持续导致 Worker 崩溃的事件被无限重试——每次崩溃都清零，它就永远到不了最大尝试次数，一直卡在那里拖累队列。不清零的话，它试满次数后正常进入死信，暴露出来让人处理。

**追问：那如果这个坏事件把每个 Worker 都搞崩呢？**

理论上可能（比如某个 payload 触发解析 bug）。这就是为什么 `WORKER_LOCK_TIMEOUT_SECONDS` 默认给 120 秒——足够长到不会误杀正常投递，也足够短到能在几分钟内恢复。更彻底的方案是把投递放到子进程里做隔离，但对这个规模过头了。这是我明确记录的已知局限之一。

### Q7：压测发现了什么问题？（这题体现量化能力）

**一句话回答**：找到并发拐点正好等于连接池上限，说明瓶颈不是 CPU 也不是数据库，而是连接池队列——请求在等连接，等待时间直接变成了请求延迟。

**展开**：

跑并发梯度时的数据：

| 并发 | 吞吐（事件/秒） | P50 | P99 |
| ---: | ---: | ---: | ---: |
| 5 | 381 | 12.7 ms | 30.3 ms |
| 10 | 360 | 25.4 ms | 63.9 ms |
| 20 | 332 | 50.0 ms | 239.3 ms |
| **30** | **145** | 140.5 ms | 728.9 ms |
| 50 | 106 | 332.7 ms | 2146.5 ms |
| 80 | 82 | 610.7 ms | 4286.3 ms |

20 到 30 之间吞吐腰斩。**30 这个数字引起了我的注意**——它正好等于连接池配置 `pool_size(10) + max_overflow(20)`。

推测：超过这个数之后，请求拿不到连接，只能阻塞等 `pool_timeout`（30 秒）。排队时间直接计入请求延迟，同时因为大量时间花在等待上，吞吐反而下降。这是典型的"过度并发"——加压不仅没提升吞吐，还让每个请求都变慢。

**验证方式**：把池上限提到 80，重测同一并发：

| 连接池上限 | 并发 | 吞吐 | P50 | P99 |
| ---: | ---: | ---: | ---: | ---: |
| 30 | 50 | 106 /s | 332.7 ms | 2146.5 ms |
| 80 | 50 | **219 /s** | 129.2 ms | 914.7 ms |

吞吐翻倍、P99 降到 43%，假设成立。

**结论与改动**：把连接池规格从硬编码改成配置项（`DB_POOL_SIZE` / `DB_MAX_OVERFLOW`）。**改配置项而不是改大默认值**，是因为合理值取决于部署环境的规格——免费层的小容器和自建服务器不是一回事，写死就意味着每次调参都要改代码重新构建。

**这题还想传达的一点**：最优并发是 5~20，不是"越高越好"。README 里我把 380 事件/秒写进了已知局限作为真实上限，而不是笼统说"高性能"。

### Q8：入站签名怎么防伪造和重放？

**一句话回答**：用 HMAC-SHA256 对"时间戳 + 请求体"签名，时间戳超出容忍窗口就拒绝，同一个时间戳的签名无法复用到另一个请求体上。

**展开**：

签名对象是 `f"{timestamp}." + raw_body`，密钥是创建 endpoint 时下发的那把。三个设计点：

1. **把时间戳纳入签名范围**，而不是只签 body。如果只签 body，攻击者拿到一个合法请求后可以无限次重放。把时间戳签进去之后，重放会被时间戳容忍窗口（默认 300 秒）挡掉。
2. **签的是原始字节，不是解析后的对象**。如果用 `json.dumps` 重新序列化再签，键顺序、空格、Unicode 转义方式的差异会导致签名对不上——而且不同语言的 JSON 实现行为不一样，签名算法必须定义在字节层面。
3. **用 `hmac.compare_digest` 做恒定时间比较**，而不是 `==`。普通字符串比较会在第一个不同字节处提前返回，理论上可以通过响应时间差异逐字节猜出正确签名。

**局限（要主动说）**：时间戳容忍窗口意味着被截获的请求在 300 秒内仍然可以重放。彻底解决需要服务端记录已用过的签名（nonce 表），代价是每次入站都要写一次数据库。对 Webhook 这个场景，300 秒的窗口加上传输层加密已经足够了，所以我选择不引入这个成本——**这也是一个取舍，而不是疏忽**。

## 三、三个真实踩坑故事

面试里讲一个"我遇到什么奇怪问题、怎么定位的"往往比讲十个功能点更有说服力。以下三个都是实际发生并解决的。

### 故事一：测试覆盖率显示 95%，但改动代码后覆盖率完全没变化

**现象**：升级测试覆盖率工具配置后，`app/api/ingest.py` 显示覆盖率 53%，而我明明为它写了大量测试。更奇怪的是，**修改被测代码后覆盖率数字纹丝不动**——说明工具根本没有在追踪这些行的执行。

**定位过程**：

1. 先怀疑测试没跑起来 → 加 `-v` 看输出，测试确实在跑，断言也确实在验证行为
2. 再怀疑是异步代码的问题 → 检查 `pytest-asyncio` 配置，事件循环模式正常
3. 关键线索：**只有调用了数据库的代码没有被追踪**。`ingest.py` 里被漏掉的行，恰好都在 `await session.execute(...)` 之后

这指向了 C 扩展的问题。数据库驱动 `asyncpg` 是编译过的 C 扩展，覆盖率工具默认用 `ctrace` 方式追踪代码执行（依赖 Python 的 `sys.settrace` 机制），而这类机制在进入 C 扩展后，返回时的帧追踪会丢失。

**解决**：切换到 PEP 669 定义的 `sys.monitoring` 机制（在配置里写 `core = "sysmon"`）。这是 Python 3.12 引入的新追踪接口，绕开了老机制的这个问题。切换后 `ingest.py` 覆盖率从 53% 跳到 93%，总体从 79% 到 95%。

**这题体现什么**：报出 95% 覆盖率不难，难的是**意识到这个数字可能是错的**。如果我没去检查"为什么改了代码覆盖率不变"，就会带着一个虚假的指标（而更糟的是，它掩盖的正是最需要测试的那部分代码——数据库交互逻辑）。

### 故事二：Docker 环境里所有事件永远停在"投递中"

**现象**：本地跑一切正常，但用 Docker Compose 起服务后，事件永远停在 `delivering` 状态，从不变成成功或失败。

**定位过程**：

1. 看 Worker 日志，找到真正的报错：`h11._util.LocalProtocolError: Too little data for declared Content-Length`
2. 这个错误说明：**声明的 Content-Length 比实际发送的字节数大**
3. 顺着这条线查，发现出站请求的 headers 里带着入站请求的 `Content-Length`，被原样透传了

**根因**：

入站请求的 headers 被完整存进数据库，投递时又完整取出来用作出站 headers。但**出站 body 不是原始字节**——事件存在 JSONB 字段里，取出来时要重新序列化（用 `separators=(",", ":")` 紧凑格式），字节数和上游原始请求不一样。HTTP 客户端看到 headers 里已经有 `Content-Length`，就照用不误，于是声明长度大于实际长度，协议层直接报错。

**为什么本地测不出来**：本地演示时用的请求体恰好是紧凑格式，重新序列化后长度没变，`Content-Length` 正好是对的。**只有请求体里带空格或非 ASCII 字符时才会暴露**。

**修复与一个关键判断**：

修法是在构造出站 headers 时剥离逐跳（hop-by-hop）头——包括 `Content-Length`、`Transfer-Encoding`、`Host`、`Connection` 等，这些头本来就不该跨代理转发。

关键判断是：**过滤必须放在出站层，而不是入站层**。直觉上"入站时不要存这些头"就够了，但历史数据里已经存过 `Content-Length` 了——如果只改入站过滤，那些旧事件在重放时会再撞一次同样的错误。放在出站层才能同时覆盖新数据和老数据。

**这题体现什么**：一是对 HTTP 协议细节的理解（为什么逐跳头不能转发、Content-Length 与 body 的一致性要求）；二是**考虑了数据的历史状态**，而不是只修"从现在开始"的路径——这在生产系统里非常关键，因为库里永远有你没预料到的老数据。

### 故事三：本地一切正常的连接串，上了云直接抛异常

**现象**：本地连 Homebrew 装的 PostgreSQL 好好的，部署到云数据库后，应用启动直接报 `TypeError`，异常信息完全指向驱动内部。

**定位过程**：

1. 看云平台给的连接串：`postgresql://user:pass@host/db?sslmode=require&channel_binding=require`
2. 本地连接串：`postgresql://localhost:5432/hookrelay_dev`，什么参数都没有
3. 差异就在这几个查询参数上。查驱动文档发现：`sslmode` 是 **libpq**（PostgreSQL 官方 C 客户端库）的参数名，而 Python 的 `asyncpg` 驱动不认这个名字，它用的是 `ssl`

**修复**：在配置层加了一个连接串规范化函数，做三件事：

- 把 `postgres://` / `postgresql://` 前缀统一成 `postgresql+asyncpg://`（SQLAlchemy 需要的方言前缀）
- 把 `sslmode=require` 改写成 `ssl=require`（两者取值恰好同名，改名即可）
- 删掉 `channel_binding`、`gssencmode` 等 libpq 专有参数（asyncpg 不支持，留着会报错），其他不认识的参数原样保留

**为什么放在配置层**：应用、Alembic 迁移、Worker 三个入口都从 `settings` 读取数据库地址。转换只做一次，才能保证三者连的是同一个库、用同一套参数。

**这题体现什么**：这是个**只在跨环境时才暴露的问题**——本地永远测不出来，因为本地根本不会有这些参数。它说明"本地能跑"和"能部署"是两件事，也说明**看懂云平台给的连接串格式**是部署的基本功。

### 故事四（附加）：压测脚本报出的吞吐比理论上限还高

**现象**：压测报告显示投递吞吐 3795 事件/秒。但 Worker 并发是 10、单次投递平均 8ms，理论上限应该是 `10 / 0.008 = 1250`。**报出来的数字超过了理论上限**，这不可能。

**定位**：看脚本实现，发现投递吞吐是用"排空耗时"做分母算的。但压测期间 Worker 一直在跑，**绝大多数事件在入站还没发完的时候就已经投递完成了**，最后剩下的只是尾巴。用尾巴的耗时做分母，自然算出虚高的数字。

**修复**：改用端到端口径——从发出第一个事件到全部投递完成的总时长。同时把"理论上限"也打进报告，**让不可能的数字自己暴露出来**。

**这题体现什么**：**对自己产出的数据保持怀疑**。一个漂亮的数字如果没有物理意义支撑，它多半是错的。压测最容易犯的错不是测得少，而是把一个错误的数字当真并写进文档——那样面试官一问"这是怎么测的"就露馅了。

## 四、可能被追问的细节

提前准备好这些，避免被问到时卡壳：

| 追问 | 准备方向 |
| --- | --- |
| 为什么选 PostgreSQL 不选 MySQL？ | JSONB 存事件体、部分索引、`SKIP LOCKED`、云平台免费层基本只给 PostgreSQL |
| 重试间隔怎么算的？ | 指数退避 `base * 2^n`，封顶 3600 秒，乘一个 ±20% 的随机抖动（避免大量失败事件同时重试形成尖峰） |
| 哪些 HTTP 状态码算可重试？ | 5xx 可重试，4xx 不可重试（除非 408、429）。3xx 归为不可重试——重定向通常意味着目标地址配错了，重试没意义 |
| API Key 怎么存的？ | 只存哈希（Argon2），明文只在创建时返回一次 |
| 下游的签名密钥怎么存的？ | Fernet 对称加密，密钥从 `SECRET_KEY` 派生。所以 `SECRET_KEY` 丢了就解不开——这一点写进了 README 的配置说明 |
| 日志怎么追踪一次请求？ | 中间件生成 `request_id` 放进 `contextvars`，JSON 日志格式化器自动带上，Worker 侧也复用同一个字段 |
| 为什么日志用纯 ASGI 中间件而不是 `BaseHTTPMiddleware`？ | 后者会包装 `receive`，在流式读取请求体（入站有大体积检查）时引入额外缓冲，且会吞掉部分异常行为 |
| 测试为什么不用 SQLite？ | `SKIP LOCKED`、JSONB、部分索引都是 PostgreSQL 特有行为，用别的数据库测等于没测 |
| 优雅关闭怎么做的？ | `start.sh` 转发 SIGTERM 给子进程，Worker 收到停止信号后不再取新任务，等当前批次投递完才退出 |

## 五、一句话总结这个项目

如果面试官问"用一段话说说这个项目"，可以这样讲：

> 这是一个 Webhook 中继服务，解决的问题是：直接转发 Webhook 会被对端的响应速度拖慢、对端故障时事件会丢、事后无法追溯。我的做法是用 PostgreSQL 表同时承担队列职责，入站只做校验和落库后立刻返回，转发交给独立的 Worker 进程异步完成，失败按指数退避重试，最终失败进死信等待人工重放。整个过程中不引入 Redis 或消息中间件，因为在这个规模下多一个组件就是多一份运维负债，而 PostgreSQL 的 `SKIP LOCKED` 已经提供了需要的全部队列语义。
